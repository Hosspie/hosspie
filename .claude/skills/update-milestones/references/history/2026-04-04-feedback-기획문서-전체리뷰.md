## 배경

서비스 기획 초기 단계에서 세워본 3대 문서(PROJECT.md, REQUIREMENTS.md, ROADMAP.md)를 CEO 관점에서 리뷰. 비전·방향성·마일스톤 구조의 정합성을 점검하고, M1의 쐐기와 M2로의 연결 고리를 검증.

## 핵심 판단

### 1. M1의 목표는 수익이 아니라 사용자 확보

M1은 무료 도구로 게스트하우스 사장님을 모으는 단계. 수익 전환은 M2 이후. 따라서 M1의 성공 지표는 "유료 전환율"이 아니라 **"계속 쓰는가"**로 측정해야 함.

### 2. M1의 와우 포인트 3가지

| 와우 포인트 | 기존 방식 | Hosspie |
|------------|----------|---------|
| 스마트 스케줄링 | 구두/엑셀로 정함 | 가능·불가능 날짜 등록 → 자동 균등 분배 |
| 교체 요청 플로우 | 카톡으로 "바꿔줘" → 구두 합의 | 앱에서 교환 요청 → 상대방 수락 → 자동 반영 |
| 인수인계 체계화 | 구두 전달, 메모장 | 인터랙티브 운영 매뉴얼 + 일일 인수인계 노트 |

**인수인계 체계화가 M1의 핵심 차별점.** 스케줄 앱은 많지만, 게스트하우스 인수인계 특화 도구는 시장에 없음.

### 3. M1→M2 브릿지 필요 (기존 스펙에 없던 부분)

기존 M1은 스태프 관리만 다루고, M2에서 갑자기 게스트 웹 서비스가 등장하는 구조였음. 연결 고리가 없으면 M2가 "완전히 다른 제품"처럼 느껴질 위험.

**추가할 브릿지 요소:**

1. **게스트하우스 정보 등록** — 스태프 업무 내용, 게스트하우스 소개, 방 정보, 저녁 파티 방식 등을 사장님이 입력
2. **간편 게스트 등록** — 네이버 예약 캡처, 인스타 DM 등을 사진/텍스트로 붙여넣기 → 게스트 자동 등록 → 개인화된 안내 문자 자동 발송
3. **QR 체크인 + 미니 게스트 웹** — QR 스캔 → 체크인 완료 표시 + 사장님 알림, 게스트는 저녁 파티 참석 여부·포틀럭 음식 등록 가능

이 브릿지가 있으면 M2(채팅, 장소 공유)는 "이미 쓰던 게 확장"으로 자연스럽게 이어짐.

### 4. 문서 구조에 대한 평가

**잘 된 점:**
- 문제 정의가 구체적 (현실 사례 기반)
- 마일스톤 순서가 논리적 (운영 도구 → 게스트 경험 → 수익화)
- 앱 구조(Admin + Guest Web) 분리가 명확
- 수익 모델이 마일스톤과 연동되어 있음

**보완할 점:**
- M1 성공 지표가 부재 — "게스트하우스 10곳 도입"은 있지만 M1 단독 기준이 아님
- M1→M2 브릿지 요소가 REQUIREMENTS.md에 반영되지 않음
- 각 마일스톤의 예상 기간/우선순위 가중치가 없음 (1인 개발이므로 시간 리소스 관리 중요)
