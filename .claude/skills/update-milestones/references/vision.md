# Hosspie 서비스 비전

> 이 문서는 CEO 스킬 실행 시 자동으로 참조되며, 리뷰 결과에 따라 갱신됩니다.
> **범위**: 비전, 핵심 가치, 문제 정의, 대상 사용자, 앱 구조, 차별점, 수익 모델. 구체적인 구현 단계나 기능 명세는 이 문서에 포함하지 않습니다.

## 한 줄 비전

게스트하우스 사장님, 스태프, 게스트들 간의 유기적 연결을 통해 게스트하우스 운영과 경험을 혁신하는 올인원 플랫폼.

## 핵심 가치

- **유기적 연결**: 사장님↔스태프↔게스트 세 축이 하나의 생태계 안에서 자연스럽게 연결
- **운영 자동화**: 수작업으로 하던 스케줄 관리, 체크인 추적, 인수인계를 스마트하게
- **게스트 경험**: 게스트들끼리 소통하고, 장소를 공유하고, AI가 코스를 추천하는 새로운 여행 경험
- **올인원 생태계**: 구인→채용→운영→예약→게스트 소통까지 하나의 플랫폼에서

## 문제 정의

현재 게스트하우스 운영 현실:

- 스태프 스케줄을 수기/엑셀로 관리, 교체 요청은 카톡으로
- 스태프 교체 주기가 빠른데 매번 인수인계가 구두로 이루어짐
- 게스트 채팅방을 사장님이 카카오톡/오픈채널로 매번 직접 생성
- 게스트들끼리 대화하다 주제가 끊기면 어색해지는데, 자연스럽게 대화를 이어갈 수 있는 장치가 없음
- 게스트 체크인을 문자로 확인하거나 셀프 체크인에 의존
- 예약을 인스타그램 DM, 네이버 예약, 야놀자, 여기어때, Airbnb 등 여러 채널로 받아야 함 (채널 파편화)
- 게스트들이 매번 맛집/코스 정보를 처음부터 공유해야 함
- 다음 날 같이 놀러 갈 때 어디 갈지 정하는 게 항상 어려움
- 스태프 구인을 네이버 카페 등 별도 플랫폼에서 진행, 채용 후 연결이 끊김

## 대상 사용자

| 사용자 | 접점 | 핵심 니즈 | 진입 시점 |
|--------|------|----------|----------|
| 게스트하우스 사장님 | Admin App (모바일) | 운영 효율화, 비용 절감 | M1 (무료 베타) |
| 스태프 | Admin App (모바일) | 근무 관리, 업무 파악 | M1 (사장님이 초대) |
| 구직자 | Guest Web (구인구직 탭) | 게스트하우스 스태프 구직 | M2 *(잠정)* |
| 게스트 | Guest Web (나의 숙박 탭) | 소통, 장소 공유, 예약 | M3 *(잠정)* |

## 앱 구조

| 앱 | 대상 | 기술 스택 | 역할 |
|---|---|---|---|
| **Admin App** | 사장님 + 스태프 | Expo/React Native | 운영 관리 허브 |
| **Guest Web** | 게스트 + 구직자 + 일반 | Web (마이크로 프론트엔드) | 하나의 웹 서비스, 탭 단위로 기능 분리 |

### Guest Web 탭 구조 *(M2 이후 잠정)*

```
hosspie.com
├── 홈 탭       : 실시간 핫플/대화 주제, 게스트하우스 소개 콘텐츠 (유입 채널)
├── 구인구직 탭 : 스태프 공고 탐색 + 지원 (M2)
├── 나의 숙박 탭: 체크인, 오늘의 게스트 채팅, 장소 공유, AI 코스 (M3)
└── 예약 탭     : 게스트하우스 탐색 + 숙박 예약 (M4)
```

## 시장 & 타겟

- **초기 타겟**: 제주도 소규모 게스트하우스 (스태프 2~3명 규모). 파티·포틀럭·커뮤니티 문화가 강한 생태계.
- **확장 가능성**: 전국(서울/부산/경주 등). 지역별로 채널 믹스가 다름 (제주: 네이버+인스타 DM, 타 지역: 야놀자/여기어때/Airbnb 비중 높음).
- **설계 원칙**: M1은 제주도에서 시작하되, 데이터 모델·아키텍처는 전국 확장 가능하게 가져간다. 파티/포틀럭 같은 제주 특화 개념은 "이벤트" 상위 추상으로 설계.

## 차별점

- **운영 매뉴얼 특화**: 스케줄 앱은 많지만(마이듀티, 듀팅 등), 게스트하우스 신규 스태프 자동 온보딩·운영 매뉴얼 도구는 없음
- **수간호사+간호사 통합 UX**: 간호사 근무표 시장은 "관리자용 자동 생성기"와 "개인용 캘린더"로 분리되어 있음. 게스트하우스 사장님은 두 역할을 한 앱 안에서 써야 하는데, 통합 솔루션이 없음
- **피드백 주도 확장**: M1은 최소 MVP로 시작, 실제 사장님 사용 피드백으로 M2~M4 방향을 결정 (가설 기반 설계 지양)
- **멀티 채널 예약 인박스** *(M4 잠정)*: 기존 PMS는 호텔용 과잉 설계. 소규모 게스트하우스용 "네이버+야놀자+여기어때+Airbnb+인스타 DM 통합 인박스"는 블루오션
- **궁극 목표**: 구인→운영→게스트→예약까지 하나의 플랫폼으로 연결. 채용 확정 순간 스태프로 자동 흡수, 예약 확정 순간 게스트로 자동 연결.

## 수익 모델

### M1: 무료 베타

**수익 없음.** 사장님 5곳에 무료 배포하여 실제 사용 피드백을 수집하는 학습 단계. 유료 전환은 M2 이후 피드백 기반으로 결정.

### M2 이후 *(잠정 — M1 피드백 후 확정)*

| 시점 | 수익원 | 비고 |
|------|--------|------|
| M2+ | 구독 (규모별 스몰/비즈니스) | M1 사용 경험이 좋은 사장님 → 유료 전환 유도 |
| M2 | 구인 공고 부스팅 (건당) | 구직자 유입 시 건당 과금 |
| M3+ | 광고 (게스트 웹) | 게스트 웹 내 광고 |
| M4 | 예약 수수료 / 노출 부스팅 | 가장 큰 잠재 수익원 |

**구독 철학**: 마일스톤이 진행될수록 구독에 기능이 추가됨 (가격 유지 → 가치 강화 → 이탈 방지).
